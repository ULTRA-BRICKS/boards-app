# Loading investigation — 16 September 2026

> Superseded by [the confirmed-cache release](CACHE-RELEASE-2026-09-18.md): persistent encrypted board caching is now implemented, deployed and measured. The old write-rejection paragraph below is historical, not a current blocker.

## The reported screen and reproduced causes
The screenshot shows the original loading shell, not the loaded board. A clean read-only inspection of the supplied board found no script error on the Mac, so its exact long wait on the physical iPhone has not been diagnosed from a screenshot alone.
Two mechanisms were reproduced in the actual published code:
1. Service worker navigation accepted only root URLs with no query string. Even a correct `__boards_build` query bypassed cached HTML.
2. Board snapshots were in tab-scoped sessionStorage only. A new tab therefore showed the skeleton until anonymous authorization and the cloud read finished. Caching the HTML does not cache the task content.
Public baseline on an unthrottled Mac: same-tab board render 7 ms in Chromium / 11 ms in WebKit; new-tab render 455 / 416 ms; same-version query HTML TTFB 43 / 46 ms despite an active worker. These are individual runs, not field percentiles or an iPhone timing guarantee.

## Changes under review
- Same-build query links now normalize to the public `/index.html` cache key. Other version/credential queries remain excluded. Cached content is returned while network revalidation is still unresolved.
- CacheStorage read/write failure cannot turn a valid network response into a failure. Background shell requests have a 12-second budget; no new mutation or private-data cache was added.
- Register the worker at module initialization rather than waiting for the page load event.
- Cold existing-board opening uses one browser request: the server acquires the same anonymous role and performs the capability-authorized read. This route rejects documents/version fields and does not grant new privileges. It returns no token when the board read is rejected. Responses remain no-store.
- An inline boot guard is independent of the app module. A failed script shows Retry opening; an unusually slow cold connection explains the wait. Real board rendering removes this temporary view. A module-preload experiment broke failed-script retry in the WebKit fixture and was removed before release.

## Explicitly incomplete
A persistent, capability-scoped cache of confirmed private board data across tabs was proposed, but its source-file write was explicitly blocked by the tool. The implementation was not created or moved to another channel. Its pending tests are outside the test suite in `.private/pending-device-cache/` and are not counted as passing. Consequently a new tab still requires a cloud read for task content; do not claim instantaneous cross-tab/offline data restoration.

The new cold-read route reduces browser/server round trips without bypassing that storage boundary. It is not a substitute for the missing persistent data cache.
