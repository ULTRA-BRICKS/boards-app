# boards-app: результаты реального внедрения state-lib

Дата: 18 сентября 2026. Ветка `pilot/state-lib-HYP-1464`, PR9. Это отчёт об эффекте библиотеки, а не только о количестве тестов. Сравнивается исходный main `0dd04bec91785511028a6a00da7c2e4e49a489c8` с текущим приложением на TS Runtime `0.1.0-pilot.1`. Точные исходные файлы и контрольные суммы фиксирует `evaluation-full.json`; итоговые commit SHA добавляются после публикации.

## Вывод

**Универсальное ускорение не достигнуто.** При неизменном интерфейсе новое хранилище даёт явные атомарные границы, изоляцию изменяемых объектов и быстрое локальное Undo/Redo. Однако обычное изменение документа стало примерно в три раза дороже на уровне controller. В браузере выигрыш отзывчивости не появился: большую часть стоимости по-прежнему определяют полная перестройка DOM и layout. Память не показывает устойчивого выигрыша, а JavaScript-сборка увеличилась.

Это полезный результат исследования: следующий приоритет — структурное разделение данных и адресные обновления UI, а не заявление, что замена механизма state автоматически ускоряет приложение.

## Что действительно подключено

Раньше state-lib обслуживал только загрузку workspace. Теперь `apps/board/app.mjs` использует `createDocumentStore` для реального документа и истории. Через него проходят изменение заголовков и текста, добавление задач, назначение исполнителей, перемещения, Undo/Redo, получение результата асинхронной иллюстрации и сброс workspace. Старые ссылки на элементы заменены поиском текущей сущности по ID внутри команды, чтобы не менять замороженный или устаревший объект.

`Runtime.transaction` публикует документ и историю одним согласованным снимком. Исключение mutator не публикует частичную правку. Входной объект и сохранённая ссылка на draft не дают позднее изменить committed snapshot. Обычная версия сравнения доступна через `?stateBackend=baseline`; `data-document-backend` в DOM подтверждает выбранный путь.

**Границы:** авторизация, серверная CAS-проверка версии и SyncQueue не заменены. Их гарантии существовали до state-lib. Undo остаётся локальным snapshot-based; загрузка внешней версии сбрасывает историю. Нет нормализованного physical store, патчевого rebase чужих изменений, CRDT, автоматической нормализации или Wasm-пути. UI по-прежнему перерисовывает всю доску.

## Корректность и UX

Полная unit-suite: **117 passed, 0 failed**, в том числе 19 контрактов хранилища. Новый браузерный сценарий прошёл во всех четырёх сочетаниях baseline/state-lib × Chromium/WebKit. Он исполняет настоящий UI: вход в синтетический workspace, изменение заголовка, создание и редактирование задачи, перенос в другую колонку, Undo, Redo, искусственный HTTP409, сохранение локального состояния, Retry, reload, мобильную ширину и выход. Исключений страницы не обнаружено.

Эти проверки доказывают конкретные инварианты, но не «предотвращение 80% всех ошибок». Ошибка subscriber возникает после commit и отличается от rollback mutator. Глубокая неизменяемость обеспечена новым app-adapter, а не голым signal: payload ядра по-прежнему caller-owned.

## Скорость хранилища

Apple M4 Pro, 24 GiB, Node v26.7.0. Одинаковые JSON-документы: 30/300/1200 задач, максимум 200 в колонке. Три разогрева, 21 измеряемый batch по 80 изменений, чередование backend. В таблице медиана среднего времени операции в batch, миллисекунды. Создание fixture и store, сеть и DOM не входят.

| Задач | Edit baseline, мс | Edit state-lib, мс | Удорожание edit | Undo/Redo baseline, мс | Undo/Redo state-lib, мс |
|---:|---:|---:|---:|---:|---:|
| 30 | 0.014 | 0.047 | 3.29× | 0.017 | 0.000528 |
| 300 | 0.130 | 0.386 | 2.97× | 0.146 | 0.000778 |
| 1200 | 0.513 | 1.546 | 3.01× | 0.595 | 0.000840 |

Причина замедления edit видна в реализации: копия всего документа до команды, вторая копия при публикации и рекурсивная заморозка. Быстрое Undo достигается переиспользованием неизменяемого снимка, а не копированием документа при каждом шаге. Поэтому следует смотреть на абсолютную экономию: для 1200 задач примерно 0,594 мс на Undo/Redo, а не рекламировать огромный относительный множитель для операции менее одной миллисекунды. В raw JSON также есть P95 **batch-средних**, который нельзя выдавать за P95 отдельных событий.

## Скорость настоящего UI

Здесь baseline — отдельный checkout исходного приложения, а не переключатель внутри ветки, уже загружающей библиотеку. Два локальных synthetic in-memory API, Chromium, отключённый cache, 9 записанных страниц после двух разогревов на условие; по 12 реальных DOM click-событий на страницу, 108 на условие. Backend чередуются. В каждой ячейке сначала baseline, затем state-lib, мс.

| Задач | Handler + DOM, median | Handler + DOM, P95 | До следующего кадра, median | До следующего кадра, P95 |
|---:|---:|---:|---:|---:|
| 30 | 0.5 / 0.6 | 0.7 / 0.8 | 16.6 / 16.5 | 31.9 / 18.4 |
| 300 | 2.3 / 2.5 | 3.1 / 3.4 | 16.8 / 17.1 | 41.4 / 31.9 |
| 1200 | 8.7 / 9.8 | 11.8 / 12.8 | 68.2 / 68.9 | 80.6 / 79.6 |

На 1200 задач синхронная работа выросла с 8,7 до 9,8 мс, но полный путь до следующего кадра практически одинаков: 68,2 против 68,9 мс. Это указывает на доминирование общего rendering/layout пути; это интерпретация совместно с исходным полным `renderBoard`, не независимый профилировочный flamegraph. Различия P95 на малых размерах не дают основания объявлять ускорение: наблюдения внутри страницы зависимы, браузер и GC шумят.

Первое появление `.paper` в DOM на 1200 задач: median 109,3/109,6 мс, P95 113,2/113,3 мс. Это **не FCP/LCP** и не измерение production CDN. До следующего requestAnimationFrame — лабораторная метрика, **не полевой INP**.

## Память, доставка, сложность

При 1200 задачах Node retained-heap delta с 40 шагами истории: median 7 103 936 B baseline против 7 339 328 B state-lib — примерно +3,3%. Семь отдельных процессов с принудительным GC на условие; маленькие deltas чувствительны к времени сборки входных объектов. В браузере median JS heap 4 741 408/4 650 868 B; native DOM memory не входит. Эти разные измерения не доказывают общего уменьшения памяти.

Сборка JS: **95 681 → 128 747 B**, сумма gzip отдельных ресурсов **36 564 → 46 183 B** (+9 619 B, +26,3%). CSS не изменился. Source maps исключены. Сборка Boards не минифицирует исходники, а сравнительная ветка включает baseline adapter; числа относятся к реальному выходу build, не к гипотетическому оптимальному пакету.

Файл приложения вырос с 47827 до 48822 B; дополнительно появились отдельные модули document-store и loader, около 202 строк. Выделение обязанностей улучшает тестируемость, но **снижение объёма прикладного кода пока не достигнуто**. Ни этот объём, ни число тестов не являются оценкой трудозатрат разработчика.

## Матрица целей библиотеки

| Цель | Результат |
|---|---|
| Атомарные изменения и immutable snapshots | Достигнуто для подключённого документа; дополнительные защиты реализует adapter. |
| Сохранность при save conflict, retry, reload | Проверена совместимость; CAS/SyncQueue преимущественно унаследованы. |
| Быстрее обычного state/update | Не достигнуто: controller edit около 3× медленнее, UI не ускорился. |
| Быстрее Undo | Достигнуто для локальной snapshot-истории; remote-safe undo не реализован. |
| Меньше памяти/пакета/прикладного кода | Не доказано либо не достигнуто; JS и glue выросли. |
| Normalized storage с denormalized API | Не реализовано в этом runtime-пути. |
| Wasm/native/workers, formal proof | Не оценивались этой интеграцией; TS-пилот не заменяет такие проверки. |

## Воспроизведение и исследовательские направления

Команды из корня Boards: `node --test tests/*.test.mjs`; `node scripts/build.mjs`; `node scripts/build.mjs --type`; `node tests/state-lib-full-browser.mjs`; `node --expose-gc scripts/benchmark-state-lib.mjs`; `BASELINE_ROOT=/path/to/checkout-at-0dd04be node scripts/benchmark-state-lib-browser.mjs`. `PILOT_EVIDENCE` задаёт output directory, который должен быть отдельным от других активных тестов.

Полные данные: `boards-evaluation/controller-benchmark.json`, `boards-evaluation/browser-benchmark.json`, `boards-evaluation/build-comparison.json` в `state-full-integration-20260918`; сводка включена рядом с отчётом. Исследовать copy-on-write/structural sharing с сохранением rollback и escaped-draft oracle; адресные entity-подписки и keyed DOM-обновления; нормализованную патчевую историю, сохраняющую чужие правки. Критерии исследований должны использовать этот же workload и не обменивать корректность на «быстрые» незаметные мутации.

Main и production не изменены. Этот отчёт не утверждает, что вся многолетняя программа state-lib закончена.

## Заведённые задачи по результатам отчёта

Все карточки созданы в действующем проекте state-lib и привязаны к HYP-1464.

- **HYP-1499** — state-lib: устранить незакрытый Runtime после dispose из subscriber.
- **HYP-1500** — Исследовать state-lib COW/normalization: убрать тройную цену обычного edit.
- **HYP-1501** — Исследовать гранулярные подписки state-lib: убрать полный redraw и задержку кадра.
- **HYP-1502** — Исследовать общий scope/persistence API state-lib вместо разросшейся app-обвязки.

HYP-1499 — конкретный невыполненный correction gate, остальные три — исследовательские задачи с исходными цифрами, предложенными критериями, ограничениями и проверками без потери гарантий. Создание задач не считается выполнением исследований.
